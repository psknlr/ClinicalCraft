## 3. Tools

All tools validate input against `inputSchema` (hand-written validation or zod; never trust model JSON), return `ToolOutput` with localised `output` text for the model and typed `data` for UIs. Clinical tools call `ctx.dispatch(action)`; rejected actions return `ok:false` with the rejection message.

| tool | scope | readOnly | risk | args | effect |
|---|---|---|---|---|---|
| `ask_patient` | history-only | no (records asks) | none | `{question}` | runs patient (or companion) agent; output = patient reply |
| `list_options` | history-only | yes | none | `{kind: "history"\|"exam"\|"investigations"\|"interventions"\|"decisions"\|"phases"}` | names/ids only — never findings or results; history: items askable in the current phase (`historyAvailable`: a phase twin replaces what it supersedes) |
| `examine` | history-only | no | none | `{finding_id?}` or `{query}` | `examine` action (matchExam for query); output = finding (or examNotRecorded) |
| `order_test` | workup | no | investigation.risk | `{investigation_id?, query?}` | `order` action (matchOrders); ambiguous query → returns candidates, no order; `orderMatching.warnings` matching the query are appended unless their `unless` held before the order |
| `read_result` | workup | no | none | `{investigation_id, phase?}` | `read` action; output = date + text + values + notes. Without `phase`: the current phase when the test was ordered there, else the phase of its most recent order (an automatic phase change — transfer, treatment — does not hide a result just ordered); a `not-ordered` rejection names the phases it was ordered in with the exact `/read <id> <phase>`. An `available: false` record shows its authored text (not performed, referred…) plus "No result in this phase." |
| `check_vitals` | history-only | yes | none | `{}` | `vitalsAt` snapshot + alarms; before the case's monitor is attached (`monitorAttached: false`): "No monitor attached yet …", the spot checks labelled as triage readings taken by hand (not live), bedside observations (a read glucose among them) — no alarm line (nothing alarms without a monitor), no rhythm, no live monitored value; attached without its ECG leads (`ecgAttached: false`, `physiology.monitor.ecgWhen`): the live readings and "No ECG leads on yet — no rhythm." |
| `intervene` | full | no | intervention.risk; `alwaysAsk` if risk high | `{intervention_id?, query?}` | `intervene` action; output = response + harm (if contraindicated) |
| `consult` | workup | yes | none | `{role: "nurse"\|"radiologist"\|"pathologist"\|"attending", question}` | runs that NPC agent |
| `answer_decision` | history-only | no | low | `{decision_id, option_ids}` | `answer` action; output = correctness + feedback |
| `set_phase` | history-only | no | none | `{phase}` | `set-phase` action |
| `wait` | workup | no | none | `{minutes}` (simulated clock only) | `advance-time` |
| `update_workup` | history-only | yes | none | `{explanation?, plan:[{text,status}]}` | emits `plan_updated` only |
| `case_status` | history-only | yes | none | `{}` | objectives, pending orders, unlocked decisions, phase, clock |
| `finish_case` | history-only | no | low | `{}` | `finish` action |
| `walk_to` (dynamic) | history-only | yes | none | `{target}` | `dynamic_tool_call` to the web world (only registered when the front-end declares support) |

Free-text queries resolve to one item only when it leads clearly (score ≥ 0.55, ≥ 0.1 ahead); a tie among the leaders goes to the item whose matched phrase covers strictly more of the query (`matchSpecificity`: "activate the cath lab" over "go to cath lab"). An id the case does not have (models guess ids) is read leniently: the same id spelled with `_` or spaces (`blood_cultures` → `blood-cultures`); else the one id whose words include every word of the guess (`ceftriaxone` → `abx-ceftriaxone`, `nasal-o2` → `o2-nasal`); else the guess read as a free-text query with the same clear-winner rule — several candidates are `ambiguous` (named, nothing done), none is `unknown-id`. An `intervene` query that states a route of administration ("oral prednisolone", "IV adrenaline", 口服, 肌注, 雾化 …) never resolves to an item whose name and aliases state only other routes; that item is offered as a candidate instead. `examine` matches only findings of the current phase (exact ids are not filtered, so the engine still reports `phase-locked`). An unresolved query returns `data.unresolved` (`ambiguous` + `candidates`, `none`, `unknown-id`, `negated`) so learner commands can word it for a person ("Did you mean …? Type /exam <id>", numbered choices). `intervene` reads negation (ARCHITECTURE.md §3.3): an instruction that negates an item ("don't give GTN", "不要静推氯化钾", "aspirin not indicated") never acts on it; one that names no withholding item of its own ("stop the pump" does) resolves to `negated` (`withheld` + `candidates`: withholding items it may mean, `doubleNegative`) — nothing is done and the reply says why ("Nothing was done: … is an instruction not to act (not given: …)"). A tool may `precheck` a call before the approval gate (`ToolDefinition.precheck`, on every path: model tool calls, learner commands and actions, MCP): `answer_decision` on a locked decision answers only what it still needs — never its prompt or options, also not in an approval summary — and `examine`/`order_test`/`intervene` refuse an item whose `requires` the session's facility lacks (`facilityCapabilities`; no facility = no check) — learner commands print that refusal as is ("Not available here: …", not wrapped in "Not possible: …") —, and `intervene` refuses an item whose `maxDoses` was already given (`max-doses`, naming the item: "… (Alteplase)"), so no high-risk confirmation is asked for a dose that cannot be given.

In embodied mode (§12) `ask_patient`, `examine`, `check_vitals`, `order_test`, `read_result` and `intervene` are spatially gated (§12.3), the world tools (§12.4) are registered and a declared dynamic `walk_to` is not (bodies move through the world: `navigate_to` and the front-end's `Mover`); the other clinical tools (decisions, phases, `wait`, the plan, status, `finish_case`, `consult` — phone/pager) work from anywhere.

**The learner's tool set** (`LEARNER_TOOLS`, `tools/learner.ts`; review S2): the clinical tools above without the dynamic `walk_to`, plus the world tools (§12.4). The learner's tool path (`LearnerPath.runTool` in `session/learner.ts`, `clinical_action` ops, slash commands), the MCP bridge and every skill or delegated step (`runToolAs`, `session/embodied-wiring.ts`) may call only these: anything else — an NPC's tool below, a front-end's dynamic tool — is refused before validation (`data.code: "NOT_A_LEARNER_TOOL"`, status `invalid`; nothing asked, nothing revealed). `check_vitals` `data` is `learnerVitals(snapshot)` (review G3): exactly what its text shows — never `vitals.ecg` (a morphology such as `st-elevation` is an interpretation that takes a 12-lead and its reading), no rhythm off the monitor or without ECG leads, no placeholder values of a case without physiology; only the renderer's `state_snapshot` keeps the full snapshot (it draws the waveform).

NPC-only tools: `reveal_facts {fact_ids: string[]}` (patient/companion; validates ids — an id superseded in the current phase is revealed as its phase twin (`historyTwin`) —, dispatches `ask` with `via:"agent"` for each new id, returns canonical answers), `get_vitals {}` (nurse; same text as `check_vitals`, so before the monitor is attached the nurse says so, gives the readings taken by hand as such and offers to attach it — the offline nurse likewise; without ECG leads she gives the readings and says she cannot tell the rhythm; the `<monitor>` prompt section of the nurse, attending and clinician carries the same text), `get_results {investigation_id}` (radiologist/pathologist/nurse — only results the learner has read or that are ready), `get_progress {}` and `give_hint {}` (attending; `hint` action).

## 4. Agent loop (`runAgentTurn`)

```
runAgentTurn({ host: LoopHost /* toolContext, authorize (approval gate), runHooks */, agent: AgentProfile, provider, system: SystemSection[], history: ChatMessage[],
               userParts: ChatPart[], tools: ToolDefinition[], maxToolRounds, signal, emit }) → { text, messages, grounded, usage, stopReason }
```
1. Append the user message; `emit(turn_phase awaiting_model)`.
2. Stream `provider.stream()`; forward `text_delta` as `agent_message_delta`; collect tool calls (complete only when `tool_call` arrives).
3. On `finish`: append the assistant message (text + tool calls + `provider_raw` when supplied — append-only history). If `stopReason` is `refusal` → stop (emit warning); `max_tokens` with tool calls → do not run them; `pause_turn` → continue.
4. For each tool call (sequentially; read-only calls may run in parallel): validate; `PreToolUse` hooks; approval gate (§6); run; `PostToolUse` hooks; emit `tool_call_begin/end`. Return **all** tool results in **one** user message.
5. Loop while there were tool calls and rounds < `maxToolRounds` (then emit `turn_aborted max_tool_rounds`). `Stop` hook may force one more step (`stop_hook_active`, max 3).
6. Retries: `withRetry` (exponential backoff 2 s ×2 cap 60 s with jitter, `maxRetries` default 4) on retryable `ProviderErrorInfo`; emit `api_retry`.
7. Abort: check `signal` between chunks and before each tool; on abort emit `turn_aborted interrupted` and keep history consistent (drop the partial assistant turn).

**Turn bracketing.** Every `agent_message` (and `agent_message_delta`) belongs to a started turn of the speaking agent — a companion who answers history speaks in the patient's turn. Lines spoken outside any agent turn — the nurse's critical-result call, monitor alarms, scenario announcements, the authored answer to a button-style `ask` — get a synthetic turn with a fresh `turnId`: `turn_started` (`synthetic: true` — not the addressed agent's reply; e.g. the MCP bridge leaves such lines out of `ask_patient`/`consult` replies, their `notification` reaches the client as a notice) → `agent_message` → `turn_complete` (`lastMessage` = the line) → `turn_phase idle`. The idle phase is omitted while another turn of the same agent is still running (that turn's own end idles it). A synthetic turn carries the id of the submission that caused it (`""` for real-time clock ticks) and may nest inside the turn whose action triggered it (e.g. a clinician's `wait`). A staff turn's `turn_started` carries `speaker` (its case/facility display name, e.g. "He Jing (resus nurse)") so the first streamed delta is already labelled with it. Scenario lines are voiced by who the text names (event `speaker`, else inferred: nurse, monitor, a patient/companion quote — then that agent speaks it —, or the narrator "Scene"/"现场").

## 6. Approval gate (`checkPermission`) — ordered ladder, first match wins

| step | rule id | outcome |
|---|---|---|
| 1 | `scope.out-of-scope` | deny if tool scope > practiceScope |
| 2 | `rule.deny` | deny if any deny rule matches |
| 3 | `mode.plan.state-changing` | deny non-readOnly tools in plan mode (message: propose instead) |
| 4 | `tool.read-only` | allow read-only tools |
| 5 | `tool.always-ask` | ask (allowSession false) when `alwaysAsk` — unless mode bypass |
| 6 | `rule.ask` | ask if any ask rule matches |
| 7 | `session.allow` | allow if an "approved for session" rule matches |
| 8 | `rule.allow` | allow if any allow rule matches |
| 9 | `mode.bypass` / `mode.auto` / `mode.default` / `mode.strict` | per table in ARCHITECTURE §4.1 using `risk` |

Rule syntax: `tool` or `tool(specifier-glob)`, e.g. `intervene(alteplase*)`, `order_test(*)`, `examine`. Specifier = intervention/investigation/finding id or `role` for consult. Learner direct actions (`clinical_action` op) go through the same gate with agent `"learner"`, mapped to the equivalent tool (`order` → `order_test`, `intervene` → `intervene`, …). `ask` → emit `approval_request`, await `approval_response` (`abort` cancels the turn; `denied` returns the reason to the agent as the tool error; `approved_for_session` adds `tool(specifier)` to session rules).

Embodied mode (§12.3): a clinical tool's spatial check — and the acting body's scope of practice — is part of its `precheck`, i.e. before this ladder (a call that cannot run at this place, or by this body, asks nobody); an operation with a clinical effect (`interact_object`, a `world_action` op, a delegated or skill step) runs the clinical tool through this same ladder with the clinical tool's own specifier — `deny: ["intervene(alteplase)"]` also stops a device that would give alteplase.

**World-tool specifiers are canonical ids** (review S6), never the caller's spelling: `interact_object` → `"<operation> <resolved target id>"`; `approach_object` / `look_at` → the resolved id; `navigate_to` → every leaf of the goal (a `target`'s entity, each leaf of an `any` goal, the room containing a `point`); `delegate_task` → `"<task> <item>"` with the target or `params` resolved to the case's ids (`give_intervention aspirin`, `record_ecg ecg-12lead`); `execute_skill` → the skill id (`perform_ecg`, `project:<id>`) or `inline:<digest>` of an inline skill's canonical JSON. A rule matches any spelling of an entity (`eq:resus1-ecg` and `resus1-ecg`); `deny` and `ask` rules apply when they match **any** of a call's things, `allow` and "approved for session" rules only when they match **all** of them (an approval for one leaf never covers another).

### 6.1 Hook outputs — where they apply

* **PreToolUse `updatedInput`** applies on every tool path: model tool calls, learner `clinical_action` ops and slash-command tools (`/order`, `/give`, `/exam`, `/read`, …). The new input is re-validated against the tool's `inputSchema` (invalid → refused; for learners an `error` with code `invalid_action`), and then the approval gate (rules and specifiers), the engine and `PostToolUse` all see the rewritten input — a hook cannot launder a denied action into an allowed one, or the reverse. For a `clinical_action` the input is mapped back to the action (`actionFromToolInput`: ids and free-text queries resolve exactly as the tool resolves them; `ask_patient {question}` resolves to one history item); input that names no single case item is refused with `invalid_action` before any approval is asked.
* **PreToolUse `decision`**: `block` refuses the call; `approve` skips the approval prompt (deny rules, plan mode and the practice scope still apply).
* **UserPromptSubmit `additionalContext`** is appended to the learner's message for model-backed nurse, consultant, attending, clinician and custom-agent turns. It is **withheld from patient/companion turns by design** (need-to-know, ARCHITECTURE §4.2): the patient model sees only its `PatientContext` (persona, affect, revealed and selected facts), so a hook cannot inject course notes, diagnoses or results into the patient's voice. `SessionStart` context follows the same rule: it reaches the system prompt of those agents, never the patient's or companion's (nor the examiner's, which judges from the transcript alone).
* **PostToolUse `additionalContext`** is appended to the tool result the model sees (model tool calls only).

## 10. Transcripts & resume

JSONL lines per `TranscriptItem` (a `diagnostic` item — e.g. the detailed grounding violations of a rejected patient reply, which may quote an unasked fact or a diagnosis — is written to the transcript only, never emitted as an event, and ignored by resume; the learner's `warning` names the violation categories). Resume: read items → `actions` (accepted only) replayed through `reduce`, per-agent `message` items restore conversations, `dialogue` items restore the examiner's evidence lines (ACTION narrations, notes, rationales; older transcripts rebuild them from messages and accepted actions) — only entries whose `who` is the learner, an engine actor or one of the session's agents, and an ACTION line only when it is the narration of the next accepted replayed action (a transcript or snapshot cannot add "ACTION: explained the diagnosis"); an engine actor's entry (`learner`, `agent`, `system`, `replay`) must have `speaker` = `who`, and an agent's entry may not carry a reserved label ("ACTION", "LEARNER"), so no entry renders as "ACTION (system): …" (`renderDialogue` labels such a speaker by its `who` too), `session_meta` restores case/locale/provider. Items replay by ordinal within a recording segment; a later `session_meta` whose ordinal does not continue the sequence starts a new segment, so a resume that restarted its ordinals never interleaves with the first run. `SessionSnapshot` carries `nextOrdinal` and `dialogue`, so a front-end resuming from a snapshot into the same transcript (the web) continues the ordinals and keeps the evidence. `clinicalcraft --resume <id|prefix|path>` / `--continue` (the most recently started session recorded by this machine, whatever its cwd or front-end). Web uploads (`<sessions>/web/`, written by `POST /api/transcripts/:id`) are untrusted: `sessions list --web` lists them (terminal-sanitised, as `sessions show`), only an exact id (their file name) or path resumes one, and never with its recorded provider/model or approval mode — decided on real paths, so a symlinked alias (or a symlinked home) is still an upload, and any transcript outside the local sessions tree resumes the same way.
Embodied mode: a `world` item (`{snapshot: WorldStateSnapshot & {elapseCarry?}}`, without engine state; the last 128 action results — the world's whole idempotency window, so a retried action id is answered from its record after a resume too — without paths, telemetry or events; `elapseCarry`: the travel-time remainder below the engine's hundredth of a minute, so a resumed clock equals an uninterrupted one — review C12) is written after every committed state-changing world action, after a front-end's world control call (`setDoor`, `setAvailability`, `setObstacle`) and at shutdown when a sensor pose moved since; `replayTranscript(items).world` is the last one and `createNodeSession` passes it as `embodied.snapshot` (resume = the engine from the actions + the world from its snapshot; monitor states derive from the restored engine). `session_meta.embodiment` records the mode (absent = clinical); `world_pose` ops are never transcribed, `world_event` events are transient, `world_action_result` events are durable.
`resumedRuntimeConfig(items)` adds the runtime state a resume continues with (passed as `restore` to `createSession`): `config_changed` patches (locale, approval mode, scope, interlocutor…), the last `plan_updated`, and the patient's/companion's emotional state — their `message` items carry `affectIntensity` (0–3, the speaker's affect when the message was recorded) and the last one per speaker is restored (`restore.affect`).

* **MCP** (`@clinicalcraft/mcp`): `runMcpServer({stdin?, stdout?, settings, env?, cwd?, content?, maxSessions? = 32, log?})` (without `content`: a `CaseLibrary` over the built-in and `settings.contentDirs` directories) JSON-RPC 2.0 over newline-delimited stdio (protocol versions 2025-06-18, 2025-03-26, 2024-11-05); `initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`, `notifications/cancelled`. Tools (34): `list_cases {locale?}` (spoiler-free titles with opaque handles — `caseHandle(id)` — never the diagnosis-bearing case ids; each case's review status — text "Clinical review: …" and `review {status, reviewedAt, text}` — and its `learningOutcomeCount`, never the outcomes' text, which names the diagnosis: the client is the learner being assessed, and `get_debrief` lists them once the case is complete; in the CLI's deterministic library order, `libraryOrder`: published cases first, then difficulty, then id — the same in every locale; `clinicalcraft://cases` lists them in the same order), `start_case {case_id, locale?, facility_id?, embodied?}` (a handle, or an exact id; no enum in the schema; `embodied` chooses the session's embodiment, default the settings' (`clinicalcraft mcp --embodied`: embodied) — an embodied session builds its own headless world, and the result adds `embodiment` and `place`; a facility with no place for the case is refused before a session opens: `structuredContent.error = "embodiment_no_slot"` with the localised reason — review C15) → session id; resources and mid-case `get_debrief` reports carry the handle, not the id; then every clinical tool from §3 except the dynamic `walk_to`, each with a required `session_id`, the 17 world tools of §12.4 (all but `get_camera_frame`; `session_id` required; `confirm` on the acting ones; read-only + idempotent hints on perception, `destructiveHint` on `interact_object`, `delegate_task` and `execute_skill`, `idempotentHint` on `cancel_action` and `transport_patient` — the same destination again changes nothing) — on a clinical session they return `isError` with `structuredContent.error = "not_embodied"` and a bilingual explanation —, plus `get_debrief`. In an embodied session every tool runs the session's own definitions (spatially gated clinical tools: a refusal carries `data.code` `SPATIAL_REQUIREMENT_UNMET` and `data.hint.goal` for `navigate_to`). An approval the session asks for inside a call (a world operation's clinical effect, a delegated or skill step) follows the same two-step confirmation, **bound to that inner act** (review S1): the first call answers it `denied` and returns `refused = {reason: "ask", ruleId, risk, confirm: "required", tool: <the clinical tool>, summary: <the step, e.g. "Give Tenecteplase …?">}` (with what the call did before, as text) and records the ask (tool, gate rule, canonical specifier and arguments); a confirmed repeat approves exactly the inner asks its refusals named — each once — and answers any other `denied`, refusing the call again and naming that step. Confirming the call itself (its own gate rule: strict mode, an always-ask skill) never approves what it asks inside; the call's own confirmation and the named inner asks accumulate across repeats until the call runs to the end (then the confirmation is used up). A skill's clinical acts done by an earlier attempt of the same call are not done again (`ToolContext.progress`: the steps are reported `resumed`), and a refused `execute_skill` lists the skill's steps ("What it does: Run the skill …: 1. intervene: Give …?; 2. …"). Cases are listed from the case index; only the started case is parsed and validated (`CaseLibrary`). Tool failures are results with `isError: true`. Resources: `clinicalcraft://cases`, `clinicalcraft://session/{id}/state`, `clinicalcraft://session/{id}/transcript` — only what the learner can see, like the tools (the client is the learner): titles and `caseId` carry the handle; the state resource adds `embodiment` and `place` (the room of the learner's body, embodied only); the transcript resource logs `world_action_result`s (`{actionId, status, errorCode, message, elapsedSeconds}`); `state.state` is the learner's own record (`LEARNER_STATE_KEYS`: phase, clock, asked/examined/orders/seen/decisions/attempts/interventions, hints, notes, objectives done, `monitorAttachedAt`), never the engine's `baselineOverrides` (scenario vitals and rhythm), `firedEvents`/`trendStops` ids or `flags`, which name findings; vitals are the learner's view of the bedside (`ClinicalSession.vitalsView()`: `learnerVitals` — never the ECG morphology; nothing monitored, and no rhythm, before the monitor is attached; in an embodied session `vitals: null` with `vitalsNotInView` while the learner's body cannot see them — reviews G3/G11); the transcript's clinical events drop scenario event ids (`scenario.event` keeps its severity — the line itself is logged as said) and flag changes. Approval mode is `auto` (`MCP_DEFAULT_APPROVAL_MODE`) unless a settings layer — user/project/local file, env or a flag such as `clinicalcraft mcp --approval` — sets `approvalMode` (`mcpApprovalMode`; the shipped `.clinicalcraft/settings.json` sets none). A call the gate would `ask` about (high-risk/always-ask interventions such as thrombolysis, ask rules, strict mode…) is a two-step confirmation: the first call is NOT carried out and returns `isError: true` explaining the action and its risk, with `structuredContent.refused = {reason: "ask", ruleId, risk, confirm: "required"}`; the client asks its user and calls again with the same arguments plus `confirm: true` (an optional boolean on every state-changing tool's schema), which runs it. The confirmation is bound to that refusal: `confirm: true` counts only when it repeats a call refused as needing confirmation in the same session (same tool, input and gate rule; within 10 minutes; once) — on a first attempt it is refused like an unconfirmed call. Deny rules, plan mode and the practice scope are never overridden. Session warnings raised while a tool runs (an agent answering with the deterministic offline responder — no API key, model error, refusal —, a reply replaced by the authored answer) are returned with the result (`structuredContent.warnings`, "Notice: …" lines) and logged to stderr; every stderr diagnostic (and a caller's `log` sink) receives terminal-sanitised text (`safeLog`: client names, model/provider errors and warnings quoting model or case text lose escape sequences and control characters); `start_case` carries those of the opening. Before the case is complete `get_debrief` names no essential test not yet obtained: the text gives a count and the report's `investigations.essentialMissing` is replaced by `essentialMissingCount`. `bypass` (explicit only, e.g. `--approval bypass` or `CLINICALCRAFT_APPROVAL=bypass`) skips the confirmation and always-ask entirely — unsafe, for unattended benchmarks. Attach mode (`runAttachedMcpServer`, `clinicalcraft mcp --attach <server>`) serves the same clinical and world tools against a learner's LIVE browser session instead (§13.7): no `start_case`, no `confirm` — the learner answers approvals.
* **Web**: the case library is an index bundled at build time (`virtual:clinicalcraft/case-index`, built from packages/content by `src/build/case-index-plugin.ts` with `caseIndexEntry` — nothing generated into the repository); each full case is its own lazy chunk, loaded when a case is selected or started (`ContentIndex.loadCase`: validated with `parseCase`, LRU of 24, 4 at a time, status idle/loading/ready/invalid/failed shown under the selected case — a failed server case can be retried in place, a failed bundled chunk needs a page reload, since browsers keep a failed `import()` for the page's lifetime); facility choice uses the entries' `capabilityNeeds`. Served by `clinicalcraft serve`: facilities and catalogs from `GET /api/content/index`, cases from `GET /api/content/cases` (index entries; a case is fetched from `/api/content/cases/:id` when it is needed, revalidated by ETag); a server without that listing has its new cases fetched in full. Runs `ClinicalSession` in the browser with `resolveProvider` from the settings panel: offline (default), proxy (when served by `clinicalcraft serve`), or direct (user key; Anthropic with `dangerouslyAllowBrowser`, OpenAI-compatible fetch). Declares the `walk_to` dynamic tool. A custom direct-mode base URL is checked against the page's `connect-src` (`checkDirectBaseUrl` in `ui/panels/pause.ts`): when served, the health check's `connectOrigins` (plus the page's own origin); otherwise the page's CSP meta tag, if any. A blocked origin gets a bilingual notice under the field: configure that base URL on the server (`providers.<id>.baseUrl`) and restart it, or use proxy mode.

## 12. Embodied mode (docs/EMBODIED.md R3, R8, R9, §4–§10)

The same encounter with a body: the session runs a headless world (`@clinicalcraft/world` `createWorldRuntime`; the browser supplies a `Mover` / `CameraSensor` to animate it), the clinical tools are held to where the acting body is, and world tools let an agent look, walk and operate equipment. Clinical mode is unchanged.

### 12.1 Settings and session options

* `embodiment: "clinical" | "embodied"` (default `clinical`; CLI `--embodied`, MCP `start_case {embodied}`) and optional `perception: {visibilityRange?, fovDeg?, nearbyRange?, maxEntities?, reachability?}` (world defaults otherwise). The mode is **fixed for an encounter**: a `configure` patch whose `embodiment` differs is refused (`error` `invalid_config` with the bilingual `embodied.fixed` reason; the rest of the patch still applies, `config_changed` never carries `embodiment`), and a resume keeps the recorded mode.
* `SessionOptions.embodied?: {mover?, camera?, spawn?, snapshot?}` — the session builds the `WorldRuntime` itself from its facility, catalogs and the case binding (core `assignPatientSlot`); without a facility `createSession` throws `EmbodimentError` (`code: "embodiment_requires_facility"`, message "English / 中文", `localized(locale)`), and without a patient place that accepts the case's setting `code: "embodiment_no_slot"` (review C15: a world without the patient would refuse every act). `embodimentProblem(facility, caseDef)` tells front-ends before they start anything: `createNodeSession` throws it before a transcript is created, the CLI (`play`/`exec --embodied`) exits with a usage error and the localised reason, MCP `start_case` answers `{error: "embodiment_no_slot" | "embodiment_requires_facility"}`. `SessionOptions.skills` adds project skills, registered as `project:<id>` (never shadowing a built-in; `createNodeSession` loads them only from a trusted project — an untrusted project's skill files are reported in a `warning` and left out, like its hooks — review S8), `skillIssues` are reported as `warning`s at start.

### 12.2 Protocol additions

* Op `{type: "world_action", request: WorldActionRequest}` — the learner's own world action (web panels, MCP, tests), queued with the turns and cancelled by `interrupt`; its clinical effect runs through the learner's tool path; answered by `world_action_result`. Clinical session: `error` `not_embodied`.
* Op `{type: "world_pose", actorId, pose}` — sensor data of a human-driven body (~10 Hz): applied at once, never queued behind a turn, never transcribed; bumps only that actor's version. Clinical session: one `not_embodied` error.
* Ops `external_tool_call` / `external_tool_cancel` — an external agent's tool call in a live session (the world bridge; both modes): §13.1.
* Events `{type: "world_event", event: WorldEvent, version}` (every committed world change; transient) and `{type: "world_action_result", result: WorldActionResult}` (any actor — world tools, `world_action` ops, skills, delegations, the autopilot; durable). `session_configured.embodiment`, `session_meta.embodiment`, `SessionSnapshot.{embodiment, world}`.
* `ClinicalSessionApi.world(): WorldRuntime | null` — a stable handle (a language switch rebuilds the runtime from its snapshot behind it): perception and planning as in the world package, `execute(request)` = the learner's action (same as the op), `updatePose` = `world_pose`, `setDoor` / `setAvailability` / `setObstacle` write a transcript snapshot. `trace(): EpisodeTrace` (empty, `embodiment: "clinical"`, in clinical mode). The session class also offers `embodiment`, `tool(name)` (the registered definition — gated clinical tools and world tools; the MCP bridge runs these) and `placeLabel()` (the room of the learner's body, or "outside / a corridor").

### 12.3 ClinicalView, ClinicalPort and the spatial gate

* **ClinicalView**: the case, the engine state, the bedside snapshot (`vitalsAt` — exactly what `check_vitals` shows), the patient's bystander cues (core `patientCues`: `distressed` = a critical alarm, or no monitor and `inExtremis`; `accessory` = nasal cannula / oxygen mask from the latest oxygen intervention) and the clock.
* **ClinicalPort.invoke(actor, tool, args)**: the clinical tool through the tool path of the caller driving that body — the learner: the learner's tool path (`LearnerPath.runTool`: validation, PreToolUse hooks with `updatedInput`, `precheck`, the approval gate, PostToolUse); model agents: `executeToolCall` with their own allow-list and turn. Never a shortcut: deny/ask rules, plan mode, scope and hooks apply as for a direct call. Outcome `ok` / `denied` (gate or hook) / `cancelled` / `rejected` (engine rejection) / `spatial` (a spatial refusal: its code and `hint` kept in the world result — review C13) / `unauthorized` (outside the acting body's scope of practice: `NOT_AUTHORIZED`) / `error`, with the clinical event ids (`ev-<seq>`). `invoke` receives the world action's id (review C4): the session answers that very action's caller (a map by action id — concurrent actions never borrow another caller's tool path), and an approval pending inside it is withdrawn when the world cancels the action (the caller's and the world's signals combined — review C5; nothing committed: `CANCELLED`).
* **ClinicalPort.elapse(seconds, reason)**: simulated clocks only, between `start` and `finish`: `advance-time {minutes: seconds / 60 × realtimeScale, reason: "travel" | "procedure", by: "system"}` in hundredths, the remainder carried; static clocks never move.
* **Spatial gate** (`tools/spatial.ts`): `ask_patient`, `examine`, `check_vitals`, `order_test`, `read_result` and `intervene` map to a `ClinicalIntent` (free-text queries resolved to item ids first, as the tool resolves them). (a) In the tool's `precheck` — before the approval gate, on every path (model tool calls, learner commands, learner `clinical_action` ops, MCP) — `world.checkSpatial(actor, intent)`; failure → `{ok: false, output: "<reason>\nGo there first: navigate_to <goal> — <label>", data: {code: "SPATIAL_REQUIREMENT_UNMET", reason, message, requirement, hint: {goal, label, then?}, details}}` (`then`, on a fetch: the operation to do on arrival — `{operation: "move_to", targetId: <cart>, goal: <the patient>}`; a `clinical-prerequisite` refusal has no hint and names the act in `details.prerequisite`) (a learner op gets an `error` with that `code`). (b) Right before the engine commit (the tool's first `dispatch`/`ask`; the learner action's dispatch) the check runs again with `recheck` → `SPATIAL_PRECONDITION_CHANGED` (the body moved while an approval was pending); nothing is committed. No fallback to clinical mode. Bodies: the learner, the clinician agent and the autopilot drive `actor:clinician`; delegated staff their `staff:*` body (`ToolContext.actorId`).
* **Role authority and scope of practice** (`tools/scope.ts`, review S3; table in EMBODIED §8): before the spatial check, the `precheck` refuses a clinical act by a body whose role may not do it — no clinical class (porter, receptionist), a tool or item outside the role's scope (a nurse's intubation, a lab technician's tenecteplase) — with `{code: "NOT_AUTHORIZED", reason: "no-clinical-authority" | "tool" | "intervention" | "investigation"}`, before anyone is asked. An approval for an act a staff member's body would do names them (`"<name> (<role>): <summary>"`).
* **Vitals channels** (reviews G3/G11): `ClinicalSession.vitalsView()` → `{inView: true, snapshot}` (`learnerVitals`) or, in embodied mode where the learner's body cannot see the bedside (`checkSpatial` vitals: the attached monitor's screen within 6 m in its room, hands at the patient, a records terminal), `{inView: false, reason, message}`. It is the single source of every learner-facing vitals channel: the clinician model's `<monitor>` section ("Vitals not in view from here: …"), `wait`'s closing line, skill `vital` predicates, the MCP state resource (`vitals: null` + `vitalsNotInView`) and the REPL status line ("vitals: not in view"). Audible alarms are still announced.

### 12.5 Travel and time (EMBODIED R8)

A completed navigation charges its travel time once (`elapse(travelSeconds, "travel")`), a physical operation its duration (`"procedure"`); operations with a clinical effect charge nothing extra (the engine's `actionCosts` already do). **Front-ends with real-time ticks** (the web's `advanceRealTime`) must pause them while an agent — the autopilot, the clinician, a delegated staff member — drives a body, else the same walk is charged twice; a human-driven avatar walks in real time (`world_pose` + ticks, no `elapse`).

### 12.6 Skills (`clinicalcraft/skill@1`, `skills/`; JSON Schema `skill.schema.json`)

Data, never code: `{schema, id, name, description (LocalizedText), params: {name: {type: entity|investigation|intervention|finding|string|number, required?, default?}}, safety: read-only|physical|clinical|high-risk, preconditions?, steps: [{id, tool, args?, when?, retry?: {attempts, on: [codes]}, onError?: abort|continue}], postconditions?, recovery?: [{on: [codes|"*"], strategy: replan|alternate-provider|fetch-equipment}]}`. Templates `${param}`, `${steps.<id>.data.<path>}`, `${steps.<id>.ok}` (each must name a declared parameter or an earlier step); parameter defaults may be macros `$patient`, `$patient-monitor`, `$monitoring`, `$capability:<cap>[,…]`; predicates `{clinical: Condition}` (core `evaluate`), `{actorNear, range}`, `{entityState, state}`, `{world: WorldPredicate, target?}`, `all`/`any`/`not`. The interpreter runs each step through the calling agent's normal tool path (a gate or hook refusal is final — never retried or recovered), applies retry → recovery → onError, then checks the postconditions against the engine and the world and returns `{status: succeeded|failed|aborted|precondition_failed|cancelled, steps, postconditions, elapsedMinutes}` (a `plan` span `skill:<id>` with a `verification` child). Built-in (11): `locate_patient`, `approach_patient`, `wash_hands`, `fetch_equipment`, `perform_bedside_exam`, `perform_ecg`, `attach_monitor`, `obtain_result`, `review_imaging`, `administer_treatment`, `reassess_patient`; project skills from `.clinicalcraft/skills/*.json` of a trusted project (and `~/.clinicalcraft/skills`), registered as `project:<id>` — a `skill_id` names a built-in first, then `project:<id>` —, invalid and cyclic ones (skills that run themselves or each other) reported and not loaded; inline skills (`execute_skill {skill}`, model-proposed JSON) validated identically.

Review rules (S2, S8, G1, C8–C10):
* **Steps** call learner tools only (`LEARNER_TOOLS`, §3) — refused at validation and again on the tool path; **nesting**: a skill may run one skill or delegate one task, the skill it runs may do neither (`SKILL_TOO_DEEP`, refused in the tool's `precheck` — nobody is asked); the interpreter yields to the event loop before every step (an interrupt is never starved).
* **Predicates** test only what the learner can see: condition leaves `always`, `asked`, `examined`, `ordered`, `read`, `resultReady`, `intervened`, `decided`, `attempted`, `objective`, `phase`, `elapsed`, `hints`, and `vital` — evaluated against what the bedside SHOWS the acting body (`vitalsView`; nothing shown: false), never the hidden physiology. `flag` and `decidedFirstTry` are refused at validation. Reported postconditions never echo step outputs (`${steps.<id>.output}` stays as written; step data only when it is a short scalar).
* **Final refusals**: a refusal by a person or a hook — directly (`denied`, `blocked`) or inside a world operation (`APPROVAL_DENIED`, `HOOK_BLOCKED`) — and a cancellation are never retried or recovered; `retry.on` / `recovery.on` may not list them (`APPROVAL_DENIED`, `CANCELLED`, `HOOK_BLOCKED`, `DENIED`, `BLOCKED`, `INTERRUPTED`; a `"*"` recovery skips them). The step's `onError` still decides whether the skill goes on (`perform_ecg` resets the cart after a refused `record`).
* **`alternate-provider`** replaces the device for the REST of the skill — every later step, `when` and postcondition — and restarts from the first step that targeted it (at most 3 rebinds); `perform_ecg` finds an in-service cart nobody holds first (`find_objects {prefer_available}`).
* **Risk** (`skills/risk.ts`): `execute_skill`'s risk and always-ask are those of the most dangerous act its steps can do (a drug given directly or by a device, a test, a delegated treatment, a nested skill); an act the gate cannot know before the step runs (an item from an earlier step's output) counts as high and always asks; parameters that do not resolve: none (the run refuses them). The approval summary lists the steps ("Run the skill X: 1. navigate_to: …; 2. intervene: Give …?").
* **Clean-up**: a skill that does not succeed leaves no device it reserved reserved (the session runs the device's release operation as the same caller, without the cancelled signal — review C3).

### 12.7 Delegation (`delegate_task`)

Tasks `attach_monitor`, `record_ecg`, `obtain_iv_access`, `fetch_equipment` (target: an equipment id, or `params.capability`), `give_intervention` (target or `params.intervention`), `transport_patient` (target or `params.destination`: a device, a bed space or room, `home`; or `params.capability` — porters, nurses, paramedics and the clinical team; EMBODIED §8). The staff member — `role` (nearest of that role to the patient where the patient is now) or a `staff:<id>` — walks and operates through the action bus with its own body; the clinical part runs through the delegating caller's tool path with `actorId` = the staff body (hooks, approvals and deny rules apply; the spatial gate measures from the staff body). Result `data.delegation = {staffId, role, task, status, steps: [{operation, target?, status, code?, message}], elapsedSeconds, clockMinutes, distance, message?, refusal?}`. **Scope of practice** (review S3; EMBODIED §8): before the staff member takes a step, the task — and for `give_intervention` the item — must be within their role's scope; otherwise `status: "failed"`, `message: "not-authorized"`, the localised `refusal` and one step with `code: "NOT_AUTHORIZED"`. An interrupted delegation reports `cancelled` (review C17); whatever the outcome, the staff member leaves no device it reserved reserved (a cart prepared for a refused tracing is reset — review C3).

### 12.8 The embodied autopilot

Offline (`autopilot` op, `/autopilot`, `exec --autopilot`): each step of the case's reference solution becomes an embodied step — intent → requirement → if unmet: walk to `hint.goal`, wheel a portable provider to the bedside when the policy asks for it, take the patient to the device a study needs (`hint.then: transport_patient` — a porter when the facility has one, else the clinician; back to their bed space after the study unless the next step needs a device too), or run the device operation that carries the action out (monitor `attach`, ECG `prepare → connect → record → reset`) — → the clinical tool → verify the engine state (ordered / read / asked / examined / intervened / decided; a wait it inserts before a result is readable: the clock advanced by its minutes) — recorded as `plan` spans (`data: {tool, args, intent, status}`) with `observation`, `navigation`, `interaction`, `clinical_action`, `state_change` and `verification` children. It finishes every built-in case in its own facility, in both locales, with the clinical-mode score. With a model, the clinician gets the same tools and the embodied prompt.

### 12.9 Traces

`EpisodeTrace = {format: "clinicalcraft-trace@1", episodeId, caseId, facilityId, embodiment, spans}`; a span: `{id, parentId, kind: observation|plan|navigation|interaction|clinical_action|state_change|verification|assessment, name, actorId, startedAt, endedAt, clockStart, clockEnd, worldVersion, ok, refs: {actionId?, clinicalEventIds?, entities?, errorCode?}, data?}`. A flow (autopilot step, skill, delegation) is a `plan` span whose scope re-parents the root spans recorded meanwhile (the `refs` and `data` given when a span ends are merged over those it was started with, so a plan keeps what it set out to do); a device operation's clinical effect reads interaction → `clinical_action` (same `actionId`) → `state_change` (`data.source: "engine"`, the engine's event ids); a direct clinical tool call is a `clinical_action` with its `state_change`. Bounded at 20 000 spans. `exec --trace <file>` writes `traceJsonl(trace)`. The session itself never records `assessment`: `bench demo` appends one closing span of that kind (`name: "assess"`, `data`: steps confirmed, the audits, approvals, score; docs/EMBODIED.md §13).

### 12.10 Vision

Model capability `vision` (catalogue: follows `supportsImages` unless a rule sets it). `get_camera_frame` is offered to an agent only when the session has a `CameraSensor` and that agent's model has `vision`; `ToolOutput.images` (`{mediaType, data}` base64) travel to the model as Anthropic `tool_result` content blocks (text, then `image` blocks) and, on OpenAI-compatible wires, as a user message following the tool messages ("Image(s) returned by tool call <id>:" + `image_url` data URLs).

## 13. World bridge: an external agent in a live browser session (docs/EMBODIED.md §12, R13)

`clinicalcraft mcp --attach <server>` lets an MCP client (Claude Code, Codex, Grok CLI…) act in a learner's **live** encounter — the web world served by `clinicalcraft serve` — instead of a headless session of its own. The server only routes: the browser runs every call through its own session's tool path as the clinician, so the approval gate, deny rules, practice scope, plan mode, hooks and the spatial gate apply exactly as for the clinician agent, and approval prompts go to the learner. An attach client is **paired** with one live session: the learner's opt-in makes an attach key, shown to the learner with the live-session id, and the learner hands both to their own agent.

Contract: `packages/agent/src/bridge/protocol.ts` (isomorphic). Browser side: `connectWorldBridge` (`bridge/world-client.ts`). Attach side: `WorldAttachClient` (`bridge/attach-client.ts`), `runAttachedMcpServer` (`packages/mcp/src/attach.ts`). Server: `WorldSessionRouter` (`packages/server/src/world-sessions.ts`). Web wiring: `packages/web/src/app/external.ts` (§13.6).

```
learner's browser: ClinicalSession             clinicalcraft serve                    clinicalcraft mcp --attach  ⇄  MCP client
connectWorldBridge ─ POST   /api/world/sessions ─────▶ registry {id, secret digest,    (--world-session ls_…, --attach-key-file …)
  (attach key ak_…)                                     attach-key digest}
                   ◀ GET    …/:id/commands (SSE) ──── call / cancel ◀──────────── POST …/:id/call {correlationId, tool, args, timeoutMs}
                   ─ POST   …/:id/results ───────────▶ ack, result ─────────────▶ 200 {correlationId, result, deduplicated}
                   ─ POST   …/:id/heartbeat ─────────▶ liveness                   POST …/:id/cancel ◀── notifications/cancelled
                   ─ DELETE …/:id ───────────────────▶ unregister                 GET /api/world/sessions[/:id] ◀── list_live_sessions
                    (cookie + x-clinicalcraft-channel)                             (Authorization: Bearer + x-clinicalcraft-attach-key)
```

### 13.1 Session ops

* `{type: "external_tool_call", callId, tool, args?}` — run `tool` as the **clinician agent** through its normal tool path (`executeToolCall` with `toolsFor("clinician")`: the clinician's allow-list, practice scope and bare deny rules; validation; PreToolUse hooks; precheck — the spatial gate in embodied mode; the approval gate — an `ask` is an `approval_request` with `agent: "clinician"` that the learner answers; the tool; PostToolUse). A state-changing tool starts the encounter once the gate let it through. Queued like other work, in a clinician turn of its own: `turn_started` → `tool_call_begin` / `tool_call_end` (with `callId`) → `turn_complete` when the tool ran (ok or not), else `turn_aborted` `denied` (a deny rule, plan mode, a hook, or the learner refused) or `interrupted` (cancelled). Malformed (`callId` 1–200 characters, `tool` 1–64, `args` an object) → `error` `invalid_op`; a `callId` already queued or running → `error` `duplicate_call`. In the transcript the op is recorded like any op (so an audit shows which tool calls came from outside); resume replays its accepted actions. The browser client also sets `deadline` (ms since epoch, the browser's clock: when the caller stops waiting — a call still queued then is not run) and, only when the front-end opted in to bypass mode, `allowBypass: true`: the session enforces both when the call runs (review S4/S11, session side).
* `{type: "external_tool_cancel", callId}` — out-of-band: a queued call never runs (a `warning`, no turn); a running one is aborted (its pending approval request is withdrawn — `approval_resolved abort`; a walk stops where it is). Unknown or finished ids: nothing. An `interrupt` (the learner's stop) cancels running and queued external calls too.

Both ops are only a transport for the bridge client: nothing on the bridge can submit `approval_response`, `configure`, slash commands or any other op.

### 13.2 Routes

Every route needs the server's auth when it has a token (a token-less server is loopback-only and rejects non-loopback `Host` headers) — the **browser's** routes (registration and the channel routes) take it as the page's `cc_token` cookie (or Bearer), the **attach** routes only as `Authorization: Bearer` (never the ambient cookie or `?token=`: `401 unauthorized`). The world routes are **same-origin only**: unlike the rest of `/api/*` they get no Vite dev-origin CORS exception (`403 forbidden_origin`), and neither the channel header nor the attach-key header is offered cross-origin. **Channel** routes also need the session's secret in `x-clinicalcraft-channel` (never in a URL; wrong or missing: `403 forbidden_channel`). **Attach** routes need the session's attach key in `x-clinicalcraft-attach-key` (wrong or missing: `403 forbidden_attach_key`).

| route | who | body → answer |
|---|---|---|
| `POST /api/world/sessions` | browser | `BridgeRegistration` (≤ 16 KiB) → `201 {id, secret, heartbeatMs, expireAfterMs, pingMs}` |
| `GET /api/world/sessions` | attach | → `{sessions: LiveSessionInfo[]}` — only the sessions of the presented attach key (none without one; connected first, then newest; never a secret or key) |
| `GET /api/world/sessions/:id` | attach (key) | → `LiveSessionInfo` |
| `DELETE /api/world/sessions/:id` | browser (channel) | → `{ok: true}`; its stream ends `closed {reason: "unregistered"}`, waiting calls get `410 session_closed` |
| `GET /api/world/sessions/:id/commands` | browser (channel) | SSE (below); a new stream replaces the previous one, which is destroyed; at most 6 opens at once, then one per 2 s per session (`429 too_many_streams`, `retry-after`) |
| `POST /api/world/sessions/:id/results` | browser (channel) | `{correlationId, kind: "ack"}` or `{correlationId, kind: "result", result: BridgeToolResult}` → `{ok, accepted?}` (a late or repeated result: `accepted: false`) |
| `POST /api/world/sessions/:id/heartbeat` | browser (channel) | `{capabilities?}` (≤ 16 KiB; updates the tools the session accepts) → `{ok, heartbeatMs, expireAfterMs}` |
| `POST /api/world/sessions/:id/call` | attach (key) | `{correlationId, tool, args?, timeoutMs?}` (`args` ≤ 64 KiB of JSON — `413 args_too_large`; the body ≤ 80 KiB) → `200 BridgeCallResponse` when the browser answered |
| `POST /api/world/sessions/:id/cancel` | attach (key) | `{correlationId}` → `{ok, cancelled}` |

Errors are `{error: {code, message}}` (bilingual by `Accept-Language`): `400 bad_request` / `bad_json`, `401 unauthorized`, `403 forbidden_channel` / `forbidden_attach_key` / `forbidden_origin` / `forbidden_host`, `404 unknown_session` (never registered, or long gone) / `not_found`, `405 method_not_allowed`, `409 correlation_conflict` (the id was used for another tool or arguments) / `call_cancelled` (cancelled before the browser ran it), `410 session_expired` / `session_closed`, `413 body_too_large` / `args_too_large`, `415 unsupported_media_type` (JSON bodies only), `429 too_many_sessions` / `too_many_calls` / `too_many_streams`, `400 tool_not_available` (not among the session's capabilities), `503 not_connected` (no command stream for `connectGraceMs`) / `server_closing`, `504 call_timeout` (`acknowledged`: the browser had received it — it may still run there).

### 13.3 Messages

* `BridgeRegistration {caseHandle, title?, facilityId, embodiment: "clinical"|"embodied", locale: "zh-CN"|"en", capabilities, attachKey, previousId?}` — `caseHandle` = `caseHandle(caseId)` (`case-xxxxxxx`, the same handle MCP's `list_cases` shows; the case id names the diagnosis and never leaves the browser); `title` the spoiler-free case title (≤ 200 characters; control, escape and bidi characters removed); `capabilities` ⊆ `BRIDGE_TOOLS` = the clinical tools of §3 and the world tools of §12.4, never `walk_to` or `get_camera_frame`; `attachKey` (`newAttachKey()`: `ak_` + 32 random bytes as base64url, made at the learner's opt-in, the same for every re-registration of that opt-in; the server keeps its SHA-256 digest); `previousId` — a re-registration after the server forgot the session (expiry, restart) asks its old id back and gets it when the id is free and, if the server remembers it, was registered with the same key (so the learner's agent keeps its `--world-session`).
* `LiveSessionInfo {id, caseHandle, title, facilityId, embodiment, locale, capabilities, createdAt, lastSeenAt, connected, pendingCalls}`; ids are `ls_` + 16 random base64url characters.
* SSE events on the command stream: `hello {id, heartbeatMs, expireAfterMs, pingMs, now}` (`now`: the server's clock — call deadlines are in it); `command` — `{type: "call", correlationId, tool, args, deadline}` (deadline: server ms since epoch) or `{type: "cancel", correlationId}`; `ping {}` every `pingMs`; `closed {reason: "unregistered"|"expired"|"server_closing"}` (a replaced stream is destroyed without one).
* `BridgeToolResult {ok, status: "ok"|"error"|"denied"|"cancelled", output, data?, notices?, warnings?, approvals?: [{tool, risk, summary, decision}], truncated?}` — `output`/`data` exactly what the clinician model sees (`ToolOutput`), `approvals` what the learner decided, `notices` the learner-visible notifications raised meanwhile. Limits (`BRIDGE_LIMITS`): output 200 000 characters, data 1 MB of JSON (else dropped, `truncated`), 32 notices/warnings of ≤ 2 000 characters, 16 approvals, a call's `args` 64 KiB; the browser bounds results before sending (`boundBridgeResult`), the server rejects anything beyond them (`parseBridgeResult`).
* `BridgeCallResponse {correlationId, result, deduplicated}` — `deduplicated`: answered from a call already pending or finished under the same correlation id.

### 13.4 Delivery, dedupe, timeouts, expiry

* **Correlation ids** (`[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}`) are chosen by the attach client and are the dedupe key: a repeated `call` with the same id joins the pending call or gets the stored result (kept 10 minutes, 256 per session) — never a second run; the same id with another tool or arguments is `409 correlation_conflict`. The browser keeps its last 128 results too: a command delivered again after a reconnect is answered from them, never run twice.
* **Delivery and backpressure**: calls are written to the command stream in order within a **window of unacknowledged bytes** (1 MiB per stream; the first always goes): the browser acknowledges each call on arrival (`kind: "ack"`), which lets the next ones through; it then posts the result. A stream holding more than 1 MiB unsent (its client does not read) or not draining for 15 s is destroyed — the browser reconnects if it is alive. When the browser (re)connects, the pending calls are sent again (within the window) after the cancels it may have missed. A call whose browser has no stream for `connectGraceMs` (10 s) fails `503 not_connected`.
* **Timeouts**: `timeoutMs` 1 000–600 000 (default 120 000; approvals included). On timeout the caller gets `504 call_timeout` (`acknowledged: true` — the browser had the call: it may still run, or have run, there — check before retrying) and the browser a `cancel`. The browser compares each call's `deadline` with the server's clock (from `hello`): a call arriving after it is never started (`status: "cancelled"`), and one still queued or running when it passes is cancelled by the browser itself (+250 ms) — even when the server's cancel cannot reach it; the session gets the deadline too (§13.1).
* **Cancellation**: `POST …/cancel`, or the attach client's HTTP request going away while nobody else waits on the call (a crashed or cancelling client), sends `cancel`; a call the browser never received just ends (`409 call_cancelled`); one it received waits up to `cancelGraceMs` (30 s) for the browser's final result (usually `status: "cancelled"`; the real result when the call had already finished). The cancel of a delivered call is remembered (256 per session, 10 minutes) and sent again on **every new stream until the browser answers it** with a result — a cancel lost while the tab was offline still arrives. A cancel for a call the browser never got is answered `cancelled` and remembered: should the call arrive afterwards, it is not run.
* **Heartbeats and expiry**: the browser sends a heartbeat every `heartbeatMs` (10 s) — and whenever a server `ping` arrives and one is due (background tabs throttle timers, not network events); any channel request (heartbeat, result, stream connect) counts. A session without one for `expireAfterMs` (45 s) is removed: its waiting calls get `410 session_expired`, its stream `closed {reason: "expired"}`, and later requests to it `410` (the ids of the last 256 ended sessions are remembered, with their key digest for `previousId`). `DELETE` removes it at once (`session_closed`).
* **Limits**: 16 live sessions, at most 4 per client address (a new registration evicts that client's — else anyone's — least recently seen session without a stream, else `429 too_many_sessions`), 32 pending calls per session and 8 requests waiting on one call (repeats of its correlation id; else `429 too_many_calls`), a call's `args` 64 KiB, stream opens rate-limited per session, bodies as above; all timers are unref'd; `close()` (server shutdown) ends every stream and answers waiting calls `503 server_closing`. `WorldSessionRouter.stats()` (`RequestHandler.worldSessions`) reports sessions, open streams, pending calls, bytes in flight and buffered.

### 13.5 Security model

* **Opt-in, per encounter, revocable.** Nothing is registered until the learner switches external control on for this encounter; the learner's one-click disconnect (`dispose()` → `DELETE`), turning it off, leaving, finishing or switching the encounter, or closing the page removes it; missed heartbeats expire it. Never persisted: every encounter, new or resumed, starts off.
* **Paired: an attach key per opt-in (review S5).** The attach routes need the session's attach key as well as the server token: the token alone (a classmate's, on a shared classroom server) can neither list, read, call nor cancel another learner's session, and a decoy session registered by another token holder never appears in the learner's agent's list. `mcp --attach` requires the session id and its key (`--world-session`, `--attach-key-file` / `CLINICALCRAFT_ATTACH_KEY`) and never picks a session itself. The key lives in the page's memory only (shown in the badge, copyable) and as a SHA-256 digest on the server, compared in constant time; registrations are capped per client address.
* **Untrusted output.** What a live session returns (output, notices, warnings, titles) is forwarded to the MCP client as data: each result starts with a notice that it is the learner's simulation output, not instructions (`structuredContent.untrusted: true`), and the server instructions tell the model never to act on it (run commands, change files).
* **No new privileges.** The external agent is the clinician agent: its allow-list, scope, deny rules, plan mode, hooks and the spatial gate apply. Approval prompts go to the learner's approval dialog, labelled as the external agent's; nothing on the bridge can answer one (no route, no op, no `confirm` argument in attach mode). A learner's “approve for this session” covers the external agent's later calls of that tool and specifier, as for any agent — the learner's choice. Calls are refused while the session's approval mode is `bypass` (nothing would ask the learner) unless the front-end passes `allowBypass` (the web never does): the browser client refuses such a call when it arrives, and the session refuses it again when it runs (a call queued before a switch to bypass; only an op carrying `allowBypass` is exempt). It forwards only `BRIDGE_TOOLS` — never slash commands, configuration, approvals, transcripts or camera frames.
* **Authentication.** The server's token/cookie model guards every route (loopback-only when no token is set — on a shared machine, set a token); the attach routes take the token only as `Authorization: Bearer`, never the ambient cookie (review S10). The browser's channel additionally needs the per-session secret: 32 random bytes, returned once, kept only in the page's memory and as a SHA-256 digest on the server, compared in constant time, sent in a header (never a URL). Attach clients never see it, so they cannot post results, unregister a session or read its command stream. The CLI reads the token from `--token-file` or `CLINICALCRAFT_SERVER_TOKEN` and the attach key from `--attach-key-file` or `CLINICALCRAFT_ATTACH_KEY` (an `--attach` URL with credentials, a query or a fragment is refused) and warns when the token would travel over plain http to another host; tokens, secrets and keys never reach logs (paths only).
* **No CORS widening, no rebinding.** The world routes are same-origin only (no dev-origin exception: a local dev page cannot ride the learner's cookie — review S10); the channel and attach-key headers are not offered cross-origin; loopback-only servers reject foreign `Host` headers.
* **Spoiler-free.** Live sessions are described by an opaque case handle and the spoiler-free title; results carry exactly what the clinician model would see.
* **Bounded and fail-closed (review S9, S11).** Size, count, rate and time limits everywhere (§13.4) — a channel holder that never reads cannot make the server buffer every (re)delivered call: the unacknowledged-bytes window, the buffer and stall caps, destroyed replaced streams and rate-limited re-opens bound what a stream holds; a session that disappears answers its waiting calls at once; a lost registration cancels the browser's running calls (no orphaned approval prompt); cancelling a call withdraws its approval request; a call reported as timed out or cancelled never starts later (deadlines, re-sent cancels).
* **Audit.** Each external call is an `external_tool_call` op in the session transcript, and its tool call, approvals and clinical events are the session's ordinary durable events (the web uploads them to `serve`, embodied `world` items included); the MCP process logs each call (tool, live session, correlation id, status) to stderr.

### 13.6 Browser client: `connectWorldBridge`

```ts
connectWorldBridge({ serverUrl, session, auth?, onStatus?, onActivity?, allowBypass?, attachKey?, tools?, title?, fetch?, backoff? }): WorldBridge
WorldBridge = { status, ready: Promise<WorldBridgeStatus>, owns(submissionId): boolean, dispose(): Promise<void> }
WorldBridgeStatus = { state: "connecting"|"connected"|"reconnecting"|"failed"|"closed", liveSessionId, attachKey, activeCalls, error: {code, message} | null }
WorldBridgeActivity = {phase: "started", correlationId, tool, args} | {phase: "running", …, submissionId} | {phase: "finished", …, result}
```

`serverUrl` "" in a page served by `clinicalcraft serve` (same origin; the `cc_token` cookie authenticates), an absolute URL plus `auth.token` in Node. It makes the attach key (`status.attachKey`; `attachKey` to supply one), registers (`capabilities` = `BRIDGE_TOOLS` ∩ `session.toolsFor("clinician")`, refreshed with every heartbeat), reads the command stream (`fetch` + `parseSSE`, no EventSource; `hello.now` gives the server's clock), runs each call with `session.run({type: "external_tool_call", …, deadline})`, derives the result from the call's events (`bridgeResultOf`), posts acks and results (retried on network errors), reconnects with backoff (1 s doubling to 15 s), re-registers when the server forgot the session (asking its id back with the same key; the calls of the lost registration are cancelled), and stops on `dispose()` or the session's `shutdown_complete`. Errors are localised (`status.error.message`): `unauthorized` (open the page with `?token=`), `unsupported` (an older server), `network`, `forbidden_origin`. `ready` never rejects. `owns(submissionId)` tells whether an event's submission is an external call (e.g. to label its approval request).

**The web wiring** (implemented and tested — `packages/web/src/app/external.ts`, `ui/hud.ts`, `ui/approval.ts`, `ui/panels/pause.ts`, `e2e/external-agent.spec.ts`):

1. **Opt-in.** The pause menu (`Esc`) of a running encounter has the switch “Allow an external agent to control this session” / “允许外部智能体控制本会话” — **off by default**, never persisted (not in preferences or saves; a new or resumed encounter starts off), offered only when the page is served by `clinicalcraft serve` and `/api/health` says `worldBridge: true` (never on the Vite dev server, whose `/api/health` answers 204, nor in the standalone build). Turning it on: `connectWorldBridge({ serverUrl: "", session: game.session.session, onStatus, onActivity })` — no `auth`, never `allowBypass`. While on, the menu shows the command to run with the live-session id filled in.
2. **Indicator.** While on, a persistent HUD badge: “External agent connected” (or connecting / reconnecting / failed, with `status.error.message`), the live-session id and the attach key — each with a Copy button (clipboard; where that is not allowed, the text is selected) — the calls running (`activeCalls`) and the last one. The approval dialog labels a request whose `submissionId` `bridge.owns(…)` as the external agent's (`approval_request.agent` is `clinician`, as for the autopilot).
3. **One-click disconnect.** “Disconnect” on the badge → `await bridge.dispose()` (cancels running external calls — their approval prompts are withdrawn — and unregisters). Also disposed on turning the switch off, leaving the encounter (library, reset, import, another case), when the encounter finishes (`case.finished`, once no external call is running), and on `pagehide` (the `DELETE` uses `keepalive`); a session shutdown disposes it by itself.
4. **Bodies.** External world tools drive the learner's avatar (`actor:clinician`) through the session's `Mover`. `BrowserMover` animates with the render loop, which stops in a hidden tab: while `document.hidden` a body is treated as undrawn and put at its target at once (also a walk under way when the tab is hidden), so `navigate_to` does not stall in a background tab. WASD during an external walk aborts it — the learner keeps control (the agent sees the interrupted walk). Real-time ticks pause during every external call (each is a clinician turn: `agentDriving()`).
5. The autopilot cannot be started while external control is on (both drive the clinician; the button is disabled). An `interrupt` (the learner's stop) also cancels external calls.
6. Strings in en / zh-CN; the bridge's own errors arrive localised. Playwright: a served build, the switch, `clinicalcraft mcp --attach` paired with the id and key read from the badge driving `navigate_to`, `interact_object` (the ECG cart → the order) and an approval clicked in the dialog (labelled), a hidden tab's walk, a denial, disconnect → `session_closed`, a resumed encounter starting off — verified from `window.__QA__`.

### 13.7 MCP attach mode: `clinicalcraft mcp --attach <url>`

Flags: `--attach <url>` (the server's base URL: http(s), no credentials, query or fragment), `--world-session <id>` (**required**, or `CLINICALCRAFT_WORLD_SESSION`: the live session the learner's badge shows), `--attach-key-file <path>` (**required**, or `CLINICALCRAFT_ATTACH_KEY`: that session's attach key — never on the command line), `--token-file <path>` (else `CLINICALCRAFT_SERVER_TOKEN`, else `server.token`), `--timeout <sec>` (1–600, default 120; approvals included). The session flags (`--provider`, `--approval`, `--scope`…) are usage errors here: the live session has its own settings. `runAttachedMcpServer({serverUrl, worldSession, attachKey, token?, callTimeoutMs?, locale?, log?, fetch?})` speaks the same JSON-RPC as §11 (`initialize`, `ping`, `tools/list`, `tools/call`, `notifications/cancelled`; `resources/list` is empty).

* Tools: `list_live_sessions` (read-only: the sessions of the attach key), then every clinical tool of §3 and every world tool of §12.4 but `get_camera_frame`, with the headless server's annotations and an **optional** `session_id` — no `start_case`, `list_cases`, `get_debrief` or `confirm`.
* Selection: `session_id`, else `--world-session` — never a session picked from a list (review S5). A session that refuses the key → `isError`, `error: "forbidden_attach_key"` (“use the key shown in the learner's External agent badge”); one that ended → `session_closed` (the learner disconnected or left) / `session_expired`; an unknown id → `unknown_live_session` with the key's sessions; no session for the key (`list_live_sessions`) → “No live browser session for this attach key — open the web world … and enable “Allow an external agent to control this session””; a tool the session does not accept → `not_available` (`not_embodied` for a world tool in a clinical session).
* Each call gets a correlation id (`mcp-<random>-<n>`) and the timeout; `notifications/cancelled` cancels it in the browser (`POST …/cancel`, and the request is aborted) and the request gets no response. Results: a first line marking what follows as the learner's simulation output (data, not instructions), then the live session's `output` (+ notices, warnings and “Approvals answered by the learner: …”), with `structuredContent {session_id, tool, ok, status, correlation_id, untrusted: true, data, approvals?, notices?, warnings?, truncated?}`; `isError` when not `ok` — a learner's denial is `status: "denied"`. Server-side failures are `isError` with `error` = the bridge code (`call_timeout` + `acknowledged` — “it may still run there; check before retrying” when the browser had it —, `session_expired`, `session_closed`, `forbidden_attach_key`, `network`, `unauthorized`…) and a clear message.
